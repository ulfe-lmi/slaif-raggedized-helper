# Preparation cleanup association

Create `PreparationOwner()` before calling `prepare(preparation_owner=owner, ...)` and retain it. A capture is creator-process-only and may be claimed once. `pending` observes its actual cleanup owner. If preparation fails before returning, call `close()` to retry safe cleanup. A busy capture refuses cleanup. Ordinary cleanup failure is reported as content-free `LaunchRefused`; an interruption retains its identity and priority. An uncertain descriptor is never retried, and pending uncertainty remains explicit.

On success, the returned `PreparedLaunch` owns the same resources. Close it only at the existing parent/child drain boundary; the capture refuses to close a live handoff. It can observe eventual cleanup and can then be closed idempotently. The reservation remains borrowed. Existing calls without a capture remain supported but have no caller-specific failure association. The association does not prove GPU vacancy, authorization, deployment readiness, or model correctness. Python allocation and asynchronous interruption do not provide atomicity across every kernel boundary.

`owner.prepared` returns the same actual `PreparedLaunch` once handoff is recorded, or `None` on failure or before handoff; it refuses a busy or foreign capture. If interruption prevents the successful return from reaching the caller, this property recovers that object. Its existing close rules still apply, including confirming that no child is running or the child has drained. The capture itself cannot drain the handoff. Microscopic allocation, lock-release and kernel interruption windows remain; this is not an atomic Python return guarantee.
