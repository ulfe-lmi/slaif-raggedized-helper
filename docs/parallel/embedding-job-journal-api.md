# Owned embedding job journal v1

`make_spec(plan_bytes)` admits UTF-8 JSON with unique keys and exact fields `format` (`embedding-job-plan-v1`), `purpose` (`prepare` or `evaluate`), `dependencies`, ordered `rows`, and `codec_policy_fingerprint`. Dependencies and rows have the exact types, bounds and uniqueness rules of the [batch store](embedding-batch-store-api.md); the codec fingerprint must equal its fixed policy. Plans are bounded at 131072 bytes and 1–128 rows. These declarations contain no vector hashes or output placeholders. A plan is normalized into compact sorted JSON when persisted.

The spec is a revalidated `job_records.JobSpec` of kind `embedding`. Each ordered row yields an artifact input with ref `sha256:` plus `representation_id` and fingerprint `schema.fingerprint({'kind':'embedding-job-row-v1','row': row})`. Configuration model, encoder and runtime are respectively `sha256:` plus inventory ID, space ID and execution fingerprint. Policy is `schema.fingerprint({'kind':'embedding-job-policy-v1','dependencies': dependencies,'codec_policy_fingerprint': codec_policy_fingerprint})`; prompt is `schema.fingerprint({'kind':'embedding-job-prompt-policy-v1','mode':'no-generator-prompt'})`, the permanent semantic no-generator policy. The existing job-spec fingerprint determines the job ID. These declarations are not proof of source relationships, model execution or authorization.

`Journal(root).own(plan_bytes)` acquires the actual per-job ownership lease and returns a context manager. The root must exist as an absolute euid-owned 0700 directory. The fixed `embedding_job_journals` directory is 0700 and files are 0600 regular, single-link, digest-named entries. Pinned directory descriptors, no-follow opens and identity checks protect the immediate namespace; no caller path enters a journal name. A handle is usable only in its creator process while its context and lease are live. `owner_id` is the live lease owner. Initial PENDING is recorded with an observed wall-clock millisecond timestamp, no owner, attempt or output.

`read()` returns `(envelope, revision)` where revision is the lowercase SHA-256 of canonical envelope bytes. The envelope has exact fields `version` (1), `format` (`embedding-job-journal-v1`), `plan`, `spec`, and ordered `events`; each event has `state` and nullable `attempt`. Each read revalidates plan, spec, every record and transition. Bounds are 524288 bytes, depth 32, 20000 nodes, 64 events and 16 unique claimed attempts. Attempt IDs cannot be reused. A historical verified label does not establish current output availability.

`append(state_bytes, attempt_bytes_or_none, expected_revision, *, store=None, metadata_bytes=None)` accepts serialized job-record JSON and performs compare-and-set after a fresh read. Claimed and running owners must match the actual lease. All existing transition and timestamp laws apply. COMPLETE requires an actual `derived_store.Store` and complete canonical expected batch metadata. The metadata dependencies, rows and codec policy must equal the plan; `embedding_batch_store.load` must freshly validate the referenced container. The state and attempt output must equal ref `sha256:` plus the loaded container ID, fingerprint `sha256:` plus SHA-256 of the metadata bytes, and availability `verified`.

A new envelope is written to an exclusive private temporary file, fsynced, ownership and revision rechecked, atomically replaced relative to the pinned directory, directory-fsynced and freshly read. Failures before replacement leave the old envelope; failures after replacement can leave the new envelope even when the operation raises. Orphan stages are ignored; normal cleanup removes only its own stage. Filesystem durability depends on the underlying filesystem honoring fsync and atomic rename.

`verified_output(store, expected_metadata_bytes)` freshly reloads the typed output and compares its derived reference on every use; missing, corrupt or mismatched data refuses without rewriting history. No retry, automatic reclaim, completion repair, model execution or controller policy is supplied. A journal does not establish neural work, current ACL, hardware qualification, global GPU ownership, independent audit or MVP completion.

The tests use explicitly synthetic future timestamps for transitions; initial timestamps come from the observed wall clock. Their small synthetic vectors and process probes demonstrate persistence and ownership mechanics only.

Opening the journal directory validates its pinned identity and fsyncs the parent root before acknowledging initialization, including when the directory already exists. A parent-sync failure refuses entry and can leave the directory present; a later owner must validate and sync it again. Injected failures exercise error handling and ordering, not power-loss durability. Cleanup attempts each owned descriptor even after an error or interruption; a descriptor whose close status remains uncertain is retained for bounded cleanup. Body exceptions and interruptions are preserved; ordinary public cleanup errors are sanitized.

A valid 64-event history can contain 16 distinct claims: fifteen complete retryable-failure cycles, followed by a sixteenth claim, running state and retryable failure. A seventeenth claim would require at least 66 events under the existing transitions, so the 64-event cap prevents reaching the separate 16-attempt guard. The parser's depth and node limits also apply before plan admission, although the accepted metadata shape and 128-row limit impose tighter practical bounds on valid plans.
