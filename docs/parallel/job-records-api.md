# Job records candidate, version 1

`job_records.admit(record_type, mapping_or_utf8_bytes)` admits JSON-shaped data for `JobSpec`, `InputRef`, `Configuration`, `JobState`, `Attempt` and `OutputRef`; failures raise the input-free `RecordError("invalid job record")`. It rejects duplicate JSON keys, unknown fields, nonfinite numbers, malformed scalars and records exceeding 65,536 encoded bytes, 4,096 nodes, 256 characters per string, 128 entries per container or 128 input references. `serialize(record)` revalidates and emits bounded canonical JSON; records and nested references are frozen, including copied input collections. Use admission for untrusted data rather than exposing Pydantic validation errors. These are inert identifiers and digests, not paths, executable names, URLs or authorization.

A version 1 `JobSpec` binds its finite kind and purpose, ordered input references (kind, digest reference and fingerprint), and policy, model, prompt, encoder and runtime configuration digests. Each digest is `sha256:` followed by 64 lowercase hex characters. Runtime `null` explicitly means unknown or unqualified; it does not establish equivalence of runtimes. The `job_id` is the shared `schema.fingerprint` of the entire JSON spec plus `domain: job-spec`. Mapping key order is irrelevant; input order is meaningful. Callers must fingerprint every relevant setting within the appropriate configuration digest; the API cannot verify the completeness of an externally supplied digest. Source revision IDs include source metadata; original blob equality does not merge rights, corpus or access labels. Operator processing approval is metadata, not authentication.

`JobState` is an immutable value representing a logically mutable snapshot; replace it through `transition(previous, next_state, attempt=None)`. PENDING may move to CLAIMED or CANCELLED; CLAIMED to RUNNING or CANCELLED; RUNNING to COMPLETE, RETRYABLE_FAILED, UNKNOWN_COMPLETION, REJECTED, FAILED or CANCELLED; RETRYABLE_FAILED to PENDING. All other transitions are refused, including automatic retry or completion from UNKNOWN_COMPLETION. A retry PENDING retains the previous attempt ID and the next claim must use a different ID. Attempt IDs must be unique across the caller's complete job history; the pure function can enforce only the immediately preceding retry. Claim and running snapshots require an opaque owner ID; this is process coordination data, not a human lookup. No ownership or steal decision follows from these values or timestamps.

Terminal transitions require a separate frozen `Attempt` with matching job, attempt, outcome and output, and a consistent end time. Attempt/request IDs are opaque bounded tokens; diagnostic codes are bounded uppercase codes. Counters and times are nonnegative strict integers: known zero stays zero and unavailable counters are null. Raw upstream errors, source content and credentials do not belong in these records. A COMPLETE state may contain no output or an `OutputRef` with `missing`, `unverified` or `verified` availability. These are caller-supplied observations, not proof; this module exposes no cache-hit decision and does not inspect or validate artifacts. A missing or unverified output must never count as a cache hit. Even a `verified` assertion requires independent current artifact and dependency validation before reuse.

Objective 010 must implement output-first staging, validation, flush and atomic publication, claim ownership and locks, bounded recovery and reconciliation, retry execution and policy, and current artifact verification. No exactly-once inference, authentication, execution, service, storage or hardware qualification is provided here. Integration, CLI and full architecture assessment remain outstanding.
